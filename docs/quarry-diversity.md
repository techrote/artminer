# AM-011 Quarry diversity and neighbourhood semantics

AM-011 is a deterministic analysis layer over a **completed** AM-010 Quarry job. It does not rewrite, prune, or reorder the authoritative `.qresults` file. Dedupe groups, clusters, unusual rankings, filters, projections, and neighbourhoods are derived browsing views and can always be recomputed from the job manifest plus its verified result prefix.

## Metric normalization and weights

Each selected metric dimension retains both its raw AM-010 value and an AM-011 normalized value.

For a completed candidate population, a dimension uses deterministic population min/max normalization:

`normalized = clamp((raw - minimum) / (maximum - minimum), 0, 1)`

A metric absent from an individual candidate is marked unavailable for that candidate and is excluded from pairwise distance for that pair. A metric absent from the entire population is an explicit error. A dimension whose maximum is not greater than its minimum is marked **degenerate**, normalized to zero, and excluded from distance. This prevents constant metrics from inventing separation.

Weights are explicit non-negative values. At least one selected weight must be positive. Headless commands accept `--weights metric=weight,...`; omitted weights mean every metric present in the job has weight 1. Raw metrics remain available for filters and inspection regardless of the weight configuration.

Metric distance is weighted root-mean-square Euclidean distance over the selected, available, non-degenerate normalized dimensions:

`distance = sqrt(sum(weight * delta^2) / sum(active weight))`

This is a distance, not an aesthetic score.

## Near-duplicate detection

The default dedupe view requires **both**:

- normalized metric distance `<= 0.025`; and
- canonical-thumbnail 8x8 luminance-signature mean absolute distance `<= 0.020`.

The thumbnail signature is derived from canonical cached RGBA8 bytes. Missing, stale, or malformed thumbnail cache entries are regenerated by the existing disposable AM-010 cache path, so the cache is never authoritative.

Candidates are considered in ascending authoritative candidate index. The first candidate that starts a group remains its representative; later candidates join the first matching representative. This deliberately simple stable greedy rule makes threshold semantics and ties inspectable. Dedupe hides repeated-looking candidates from a representative view only: it never deletes a job row or recipe identity.

## Deterministic clustering and representatives

Clustering uses no third-party statistics or ML package. It is a deterministic farthest-first partition suitable for modest-to-large result sets:

1. candidates are ordered by authoritative candidate index;
2. the lowest index is the first seed;
3. each next seed is the candidate with greatest distance from its nearest existing seed; equal distances choose the lower candidate index;
4. each candidate joins its nearest seed; equal distances choose the cluster whose seed has the lower candidate index;
5. each cluster centre is the arithmetic mean of available normalized metric coordinates;
6. the representative is the member nearest that centre; equal distances choose the lower candidate index.

The headless `cluster` command applies the documented default dedupe view before clustering representatives. The reusable core API can cluster the full set or an explicitly supplied dedupe view.

## “Unusual” is explicit distance

`quarry rank` supports two bases:

- `population`: distance from the complete population centroid;
- `cluster`: distance from the candidate's deterministic cluster centroid.

Each ranking row exposes the total distance and per-metric weighted squared contribution after normalization. Contributions are sorted by decreasing contribution and then metric name. Equal total distances are ordered by ascending candidate index.

“Unusual” therefore means far from the selected centre under the visible metric/weight contract. It does **not** mean better, prettier, rarer in any external corpus, or preferred by an opaque model.

## Parameter and neighbourhood distance

Parameter distance reconstructs each candidate recipe using the authoritative AM-010 enumeration contract. Mutable parameters are ordered by stable node ID and parameter name and normalized from their node-registry domains:

- integer and real values use their declared numeric min/max;
- boolean is 0 or 1;
- enum values use stable registry order from 0 through 1.

The neighbourhood engine supports:

- `metric`: normalized metric distance only;
- `parameter`: normalized recipe-parameter distance only;
- `combined`: RMS combination of metric and parameter distance using an explicit metric weight in `[0,1]`.

An optional minimum metric-diversity floor excludes candidates that are too visually/metric-near even when their parameters are close. The native Quarry UI's **Mixed + diverse** mode uses a 50/50 combined distance and a `0.025` metric-diversity floor. Results are ordered by increasing distance with candidate index as the deterministic tie-break.

## Filtering and projection

Metric range filters operate on raw AM-010 metric values. Sorting is stable and uses candidate index for ties.

The native UI and `quarry project` expose two user-selected metric axes. Coordinates are the two corresponding normalized metrics. The UI and CLI label this explicitly as selected-axis projection and state that it is **not literal geometry for the full higher-dimensional metric space**.

## Saving discoveries

A Quarry discovery can be materialized back into a normal `.amr` recipe using the exact job manifest, candidate index, mutation-operator version, root seed, and render dimensions. Before save, the implementation checks the reconstructed semantic fingerprint against the authoritative result row.

Materialized recipes add non-semantic metadata:

- `quarry.job_identity`;
- `quarry.candidate_index`;
- `quarry.candidate_id`;
- `quarry.source_fingerprint`.

Recipe metadata is already excluded from ArtMiner semantic fingerprints, so these provenance fields do not change rendered recipe identity. The native UI and headless `quarry save` use the same normal browser-store save/favourite functions as other specimens. The resulting recipe can therefore be reopened, mutated, or used by the breeding workflow without becoming a Quarry-specific recipe type.

## Headless commands

```text
ArtMiner quarry dedupe <job.amq> [metric-threshold] [image-threshold] [--weights name=value,...]
ArtMiner quarry cluster <job.amq> <cluster-count> [--weights name=value,...]
ArtMiner quarry rank <job.amq> <population|cluster> [cluster-count] [--weights name=value,...]
ArtMiner quarry neighbours <job.amq> <candidate-index> <metric|parameter|combined> [limit]
    [--weights name=value,...] [--combined-weight value] [--min-diversity value]
ArtMiner quarry project <job.amq> <x-metric> <y-metric>
ArtMiner quarry filter <job.amq> <metric> <min|*> <max|*> [asc|desc]
ArtMiner quarry save <job.amq> <candidate-index> <recipes-root> [--favourite]
```

All analysis commands require a completed, internally verified Quarry job. Re-running the same command against the same completed job with the same explicit settings produces the same representative selection, ordering, distances, and coordinates.
